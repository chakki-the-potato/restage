# 6단계 검증 결과 — 메뉴바 UI

측정일: 2026-08-23

## 자동으로 확인한 것

프로세스 안에서 확인 가능한 범위다.

```
1s: button=true visible=true
2s: button=true visible=true
3s: button=true visible=true
메뉴 항목 6개:
  'broken' enabled=false tooltip=config 형식이 올바르지 않습니다. Path: screens[0].items[0].slot ...
  'dev' enabled=true
  'research' enabled=true
  ---
  'config 폴더 열기' enabled=true
  '종료' enabled=true
```

`MenuContent`의 단위 테스트 6개가 메뉴 구성 로직을 덮는다. 목록, 깨진 config 비활성화, 빈 디렉토리 안내, 레지스트리 오류, 실패 요약 생성.

## 사람이 확인한 것

메뉴가 정상적으로 뜨고 `dev`와 `research`가 실제로 실행됐다. 두 워크스페이스가 같은 우측 절반을 쓰므로 나중에 실행한 것이 앞에 온다.

## 메뉴바 아이콘이 보이지 않던 문제

가장 오래 걸린 부분이며, 결론부터 말하면 **코드 문제가 아니었다.**

증상은 메뉴바에 아이콘이 보이지 않는 것이었다. AX로 조회하면 항목은 존재했다.

```
restage 항목: position=(-3666, -1467) size=40x24
```

디스플레이 범위와 대조하면 화면 밖이다.

```
내장 메뉴바:  x 0..1728,    y 0..33
외장 메뉴바:  x -419..2141, y -1440..-1407
restage 항목: x -3666,      y -1467        <- 두 화면 모두 바깥
```

우리 코드가 원인인지 가리려고 최소 코드로 별개의 상태바 항목을 만들어 좌표를 쟀다. 그것도 `x = -3705`로 같은 영역에 배치됐다. 새로 만드는 항목은 무엇이든 그리 간다는 뜻이다.

`Hidden Bar`를 잠시 종료하고 다시 쟀다.

```
Hidden Bar 종료 전:  x = -3666   (화면 밖)
Hidden Bar 종료 후:  x = 1382    (화면 안)
```

Hidden Bar류 도구는 넓은 구분자를 넣어 항목들을 화면 밖으로 밀어내는 방식으로 숨긴다. 새 항목은 기존 것들 왼쪽에 붙는데 그곳이 숨김 영역이다.

### 배포에 반영해야 할 것

이 환경은 특수하지 않다. 노치 있는 MacBook에 메뉴바 관리 도구를 쓰는 구성은 흔하다. 첫 실행 안내에 다음이 필요하다.

- 메뉴바에서 아이콘이 보이지 않으면 Hidden Bar 같은 도구의 숨김 영역을 확인할 것
- `cmd`를 누른 채 드래그해 위치를 옮길 수 있다는 것

7단계의 단축키가 붙으면 이 문제의 무게가 줄어든다. 아이콘을 찾지 않아도 워크스페이스를 실행할 수 있기 때문이다.

## 실사용에서 드러난 한계

`dev`의 `safari: left-half`가 Safari의 **시작 페이지 창**을 옮겼다. 그 시점에 Safari에는 창이 둘(시작 페이지, research 전용)이었다.

1단계에서 "창이 여러 개면 가장 최근 활성 창을 배치한다"로 정한 규칙이 그대로 동작한 것이다. 다만 실사용에서는 **어느 창이 옮겨질지 예측하기 어렵다**는 점이 드러났다. 브라우저처럼 창을 여러 개 쓰는 앱에서 특히 그렇다.

지금 스코프에서 바꾸지 않는다. 대안(창 제목 매칭, 창 지정 문법)은 스키마 변경을 수반하므로 별도 결정이 필요하다.

## 자동 검증의 한계

지금까지 5단계 내내 자동 검증으로 진행했으나 GUI는 그 방식이 통하지 않는다.

메뉴 항목 구성은 `NSMenu`를 만들어 검사할 수 있지만, 클릭해서 실제로 배치되는지는 사람이 봐야 한다. 이 한계를 감추지 않고 스펙과 이 문서에 명시한다.

- 로그인 시 자동 실행. 앱 번들이 필요하다.
