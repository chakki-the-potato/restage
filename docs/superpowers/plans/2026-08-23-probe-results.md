# 1단계 검증 결과 — 창 배치

측정일: 2026-08-23
대상: 표본 9종 (cursor는 표본에서 제외)
머신: 내장 디스플레이 `frame=(0,0,1728,1117)`, `visibleFrame=(0,57,1728,1027)`, `primaryMaxY=1117`
외장 디스플레이 1대 연결됨 `frame=(-419,1117,2560,1440)`. 이번 스코프는 주 디스플레이만 다룬다.
Rectangle은 측정 중 종료 상태.

## 결과

`right-half`와 `left-half` 두 슬롯으로 각각 전체를 돌렸고 결과가 동일했다. 슬롯을 바꿔 실행하면 앱이 기억하는 크기와 목표가 달라지므로 실제 리사이즈가 강제된다.

| 앱 | 콜드 | 웜 | 시도 | 비고 |
|---|---|---|---|---|
| safari | PASS | PASS | 1 | |
| iterm | PASS | PASS | 1 | |
| xcode | CONSTRAINED | CONSTRAINED | - | 크기 고정 창 740x460 |
| iina | CONSTRAINED | CONSTRAINED | - | 크기 고정 창 640x400 |
| chrome | PASS | PASS | 1 | |
| discord | PASS | PASS | 4 | Electron 자가 리사이즈 |
| notion | PASS | PASS | 1 | |
| claude | PASS | PASS | 1 | |
| kakaotalk | PASS | PASS | 1 | |

집계: PASS 14 / CONSTRAINED 4 / FAIL 0 (18케이스). 두 슬롯 모두 동일.

소요 시간은 대부분 30~60ms, 콜드 스타트의 iterm과 chrome이 110~190ms, discord가 150ms 안팎이다.

## CONSTRAINED 사유

두 건 모두 앱이 가진 유일한 창이 크기 변경을 허용하지 않는다. `AXUIElementIsAttributeSettable`이 `AXSize`에 대해 false를 반환한다. 위치는 정상 적용된다.

- **Xcode**: "Welcome to Xcode" 창. `role=AXWindow`, `subrole=AXUnknown`, 740x460 고정. 프로젝트를 열면 리사이즈 가능한 창이 생기지만, 프로젝트 없이 기동하면 이 창뿐이다.
- **IINA**: 시작 창. `role=AXWindow`, `subrole=AXStandardWindow`, 640x400 고정. 영상을 열면 리사이즈 가능한 창이 생긴다.

둘 다 고칠 수 없는 앱 동작이므로 실패가 아니라 제약으로 분류한다.

## 검증 중 발견해 수정한 것

계획 문서만으로는 드러나지 않았고 실제 앱을 돌려서야 나온 문제들이다.

### 1. 일부 앱은 최전면이 되어야 AX 창 트리를 만든다

Safari는 창이 화면에 보이고 AppleScript가 `count windows`로 1을 반환하는 상태에서도 `AXWindows`가 빈 배열을 돌려준다. System Events로 교차 확인해도 동일하므로 우리 코드 문제가 아니라 Safari의 AX 동작이다.

`AppLauncher`가 `configuration.activates = false`로 앱을 띄우기 때문에 이 상태에 걸린다. 활성화하면 500ms 안에 창이 노출된다.

활성화 방법도 문제였다. 다음을 비교 측정했다.

| 방법 | 결과 |
|---|---|
| 아무것도 안 함 | 3초 후에도 AX 창 0개 |
| `NSRunningApplication.activate()` | 3초 후에도 0개 |
| AX `AXFrontmost = true` | 500ms 후 1개 |

`NSRunningApplication.activate()`는 호출하는 쪽이 GUI 앱이 아니면 macOS가 무시한다. 이 도구는 CLI라 그 경로가 아무 효과도 내지 못한다. AX는 접근성 권한이 이미 있으므로 동작하고, Apple Events 권한을 새로 요구하지도 않는다.

`WindowWaiter`가 750ms 안에 창을 못 찾으면 한 번만 `AXFrontmost`를 설정하고 계속 폴링한다.

### 2. Electron 앱의 스플래시 창을 본창으로 오인

Discord는 기동 직후 300x300 고정 크기 창을 띄우고 잠시 뒤 1280x870 본창으로 교체한다. 초기 `waitForWindow`는 `role`과 크기만 봤기 때문에 스플래시를 잡았고, 위치는 적용되는데 크기만 실패했다.

`AXSize`가 설정 가능한지를 조건에 추가해 스플래시를 건너뛴다. 다만 Xcode와 IINA처럼 가진 창이 전부 크기 고정인 앱이 있으므로, 4초(`splashGrace`) 동안 리사이즈 가능한 창이 안 나오면 고정 크기 창을 폴백으로 반환한다. 그래야 "창이 없다"는 잘못된 보고 대신 크기 제약이라는 정확한 사유가 나간다.

이 판별을 넣기 전에는 두 앱 모두 CONSTRAINED로 분류됐는데, Discord의 경우 실제 버그를 제약으로 덮는 것이었다. 본창이 따로 있는지 직접 확인해서 잡았다.

### 3. 배치 도중 창 요소가 무효화됨

Discord는 기동 중 창을 파괴하고 새로 만드는 경우가 있어, 잡아둔 `AXUIElement`가 도중에 무효가 된다. 그러면 `AXPosition` 조회가 실패해 "창 좌표를 조회할 수 없습니다"로 끝난다.

`AXWindow`가 소유 프로세스의 pid를 들고 있게 하고, 배치 실패 시 요소가 무효면 창을 다시 찾아 한 번 재시도한다.

### 4. 수렴 루프의 상한이 횟수였다

초기값은 3회 시도 / 3초였다. Discord 콜드 스타트는 4~7회를 쓰는데, 한 번 시도가 30~40ms라 횟수가 먼저 소진되고 시간은 한참 남았다. 상한을 40회 / 8초로 바꿔 시간이 주 제약이 되게 했다. 루프는 수렴하면 즉시 빠져나오므로 빠른 앱에는 비용이 없다.

여기에 더해 배치를 시작하기 전에 창 크기가 안정될 때까지 최대 2초 기다린다. 앱이 자체 레이아웃을 끝내기 전에 배치하면 서로 덮어쓰기를 반복한다.

### 5. `waitForWindow` 타임아웃

권장값 5초로는 Xcode가 걸린다. 실측상 Xcode는 콜드 스타트에서 창이 나오기까지 3.5초가 걸리고, 기동 중에는 AX 호출 자체가 지연되어 예산을 더 먹는다. 15초로 올렸다. 창을 찾으면 즉시 반환하므로 정상 케이스에 비용이 없다.

## 검증 방법의 한계

콜드 스타트 검증은 앱이 직전 배치 위치를 기억하면 약해진다. 목표와 같은 크기로 뜨면 리사이즈가 일어나지 않아 사실상 아무것도 검증하지 않는다. 실제로 Claude에서 이 현상을 관찰했다.

그래서 최종 측정은 `right-half`와 `left-half`를 번갈아 돌렸다. 앱이 기억한 슬롯과 목표 슬롯이 항상 다르므로 매번 실제 리사이즈가 강제된다.

## 표본에서 cursor를 제외한 이유

probe의 콜드 스타트는 대상 앱을 종료한다. 이 저장소의 개발이 Cursor 안에서 이뤄지므로 cursor를 표본에 두면 검증이 자기 자신을 죽인다. 실제로 작업 중 한 번 그렇게 세션이 끊겼다.

`AppRegistry.probeSample`에서 빼되 매핑에는 남겨서 `--app cursor`로 개별 조회는 계속 가능하다. Electron 자가 리사이즈는 discord, notion, claude 3종이 덮으므로 커버리지 손실은 없다.

참고로 Task 8·9 진행 중 단일 창 배치로는 Cursor에서 성공을 확인했다. 외장 모니터에 있던 창을 내장 화면 좌측 절반으로 첫 시도, 105ms에 옮겼다. 콜드/웜 2케이스 정식 검증은 아니다.

## 데스크탑(Space) 지정 — 검증 결과와 다음 사이클 방향

사용자가 실제로 여러 데스크탑에 앱을 나눠 쓰고 있어, 전체 스펙이 제외했던 Space 배치를 다시 검토했다.

### 우회로 검증

"목표 데스크탑으로 먼저 전환한 뒤 그 자리에서 앱을 띄우면 새 창이 거기 생긴다"는 우회로를 시험했다. 데스크탑 전환 단축키를 두 경로로 주입했고 **둘 다 전환되지 않았다.**

| 방법 | 결과 |
|---|---|
| `CGEvent`로 `ctrl+→` 주입 (`.cghidEventTap`) | 전환 안 됨 |
| System Events `key code 124 using control down` | 전환 안 됨 |

판정은 `CGWindowListCopyWindowInfo(.optionOnScreenOnly)`의 창 소유 앱 집합으로 했다. 이 목록은 현재 Space의 창만 담으므로 전환되면 반드시 바뀐다. `com.apple.spaces` plist의 `Current Space`는 지연 기록이라 판정에 쓸 수 없었다.

Mission Control 단축키 설정은 활성 상태였다(`AppleSymbolicHotKeys` id 79~82 전부 `enabled=1`). 즉 설정 문제가 아니라 macOS가 합성 키 입력으로는 Space를 바꾸지 않는다.

`ApplicationServices`에 Space 관련 공개 심볼은 0개다. 이 머신의 SIP은 enabled다.

결론: 현재 권한 모델 안에서 데스크탑 지정은 불가능하다.

### 다음 사이클 방향: yabai 선택 의존

직접 SkyLight 비공개 API를 주입하는 대신, yabai가 설치된 경우에만 그것을 호출한다.

```
yabai -m window --space 2
```

근거는 이렇다.

- SIP 부분 해제는 어느 경로로 가든 피할 수 없다. 그 위험과 macOS 업데이트 대응 부담을 직접 떠안는 대신 이미 그 문제를 푼 도구에 위임한다.
- restage 본체는 공개 API만 쓰므로 공증과 Homebrew cask 배포 경로를 유지한다.
- yabai가 없으면 해당 항목만 전체화면으로 대체되고 나머지 배치는 그대로 동작한다. 선택 의존이므로 기본 사용자는 영향이 없다.

대안으로 검토했다가 채택하지 않은 것.

- **restage가 직접 주입**: 결과는 같은데 유지보수를 전부 떠안고 배포 경로를 잃는다.
- **Dock의 앱별 "데스크탑에 지정"**: SIP을 건드리지 않는 유일한 방법이지만 설정이 수동이고 restage가 읽거나 쓸 수 없다. 보조 안내로만 문서화한다.

## 2단계 전체화면 검증 — 결과와 한계

### 결과

전체화면을 지원하는 7종(safari, iterm, chrome, discord, notion, claude, kakaotalk)에서 **전환 진입은 전부 성공한다.** 실측 좌표는 `0,33 1728x1084`이며, iTerm만 자체 여백 처리로 `0,69 1728x1048`이다.

`setMain` 수정 전에는 Claude와 Notion이 웜에서 실패했다. 앱을 최전면으로 올리는 것만으로는 부족하고 대상 창을 주 창으로 지정해야 전환이 적용된다.

전환 실패로 남은 것은 discord 웜 1건이며 재현율이 낮다(3~4회 중 1회). Electron 앱이 배치 직후 전환 요청을 흘리는 것으로 보인다.

해제는 별도 문제다. 아래 "전체화면은 편도다"를 참조.

Xcode와 IINA는 전체화면 버튼이 없어 `CONSTRAINED`로 분류된다. 프로젝트나 영상을 열지 않은 상태의 환영 창은 전체화면을 지원하지 않는다.

iTerm은 전체화면 크기가 `0,69 1728x1048`로 다른 앱(`0,33 1728x1084`)과 다르다. iTerm 자체 여백 처리이며 전환은 정상이다.

### 전체화면에서 잡은 거짓 통과 두 가지

둘 다 판정만 보면 통과였고 실측 좌표를 대조해야 드러났다.

**1. 최전면이 아니면 전환이 일어나지 않는다.** 앱이 최전면이 아닌 상태에서 `AXFullScreen = true`를 설정하면 설정은 성공으로 보고되고 속성도 true가 되지만 창 크기는 그대로다. 콜드 스타트는 창 대기 단계의 활성화 폴백 덕에 우연히 통과하고 웜 스타트만 실패해서, 원인을 엉뚱한 곳에서 찾기 쉬운 형태로 드러났다.

전환 전에 앱을 최전면으로 올리고 실제로 올라올 때까지 기다린 뒤, 대상 창을 `AXMain`으로 지정한다. 앱만 올리고 창을 지정하지 않으면 Claude에서 여전히 실패했다.

**2. 전환됐다가 되돌아온 값을 안정값으로 잡았다.** `AXFullScreen`이 true가 된 것만 확인하고 크기 변화를 안 봤다. Discord는 전환이 시작됐다가 되돌아가는 경우가 있는데, 그때 `settle`이 되돌아온 크기를 안정값으로 반환해 "전체화면 성공, 실측 864x1027"이라는 모순된 보고가 나갔다.

이제 `AXFullScreen`이 true가 되고 → 크기가 실제로 이전 값과 달라지고 → 안정되고 → 최종 크기가 여전히 이전 값이 아닌지까지 확인한다.

또한 전체화면 버튼이 없는 창은 `AXFullScreen` 설정을 시도조차 하지 않고 바로 `CONSTRAINED`로 분류한다. 지원하지 않는 동작을 찔러본 뒤 되돌리는 것보다 낫다.

### 결정적 제약 1: 전체화면은 편도다

AX만으로는 앱을 전체화면으로 **넣을 수는 있어도 뺄 수 없다.**

앱이 전체화면이 되면 macOS가 전용 Space로 옮긴다. 그런데 화면은 그 Space로 전환되지 않고, AX는 현재 Space의 창만 열거하므로 해제할 창에 도달할 방법이 없다. `AXFrontmost`를 설정해 앱을 최전면으로 만들어도 Space는 바뀌지 않는다 — `NSWorkspace.frontmostApplication`은 해당 앱을 가리키는데 `AXWindows`는 계속 빈 배열을 반환한다. AppleScript `activate`도 마찬가지다.

이걸 확인하기까지 두 단계를 거쳤다.

처음에는 해제 코드가 진입과 대칭이 아닌 것이 원인이라고 판단했다. 진입할 때만 앱을 최전면으로 올리고 대상 창을 `AXMain`으로 지정하고, 해제할 때는 속성만 끄고 있었다. 대칭을 맞췄지만 결과는 같았다. 고칠 수 없는 것을 고치려 한 것이었다.

**검증 설계에 더 큰 결함이 있었다.** 게이트가 전환 진입만 측정하고 복원 결과는 표에 넣지 않았다. 그래서 probe가 `PASS`를 찍는 동안 뒤에서 전체화면 Space가 앱마다 하나씩 쌓였고, 표에는 아무 흔적도 남지 않았다. 사용자 머신에 데스크탑 6개가 쌓이고 나서야 발견했다. 복원 여부를 결과에 반영하도록 고친 뒤에야 Space 개수가 2→3→4→5→6→7로 증가하는 것이 표에 드러났다.

교훈은 되돌리는 동작도 측정 대상이라는 것이다. 측정하지 않은 것은 실패해도 보이지 않는다.

현재는 해제 실패를 `WARN`으로 표시하고 사유를 남긴다. 실패로 뒤집지 않는 이유는 구현 결함이 아니라 플랫폼 한계이기 때문이다. 사용자가 `ctrl+cmd+F`로 직접 빠져나와야 한다.

제품 관점에서는 감당할 만하다. 워크스페이스 복원의 목적은 앱을 전체화면으로 **만드는** 것이고 그것은 동작한다. 다만 다음 두 가지가 따라온다.

- 전체화면 검증은 본질적으로 파괴적이다. 실행할 때마다 앱 수만큼 Space가 남는다. 반복 가능한 게이트로 만들 수 없다.
- 같은 워크스페이스를 두 번 실행하면 이미 전체화면인 앱은 그대로 두어야 한다. 해제 후 재배치는 불가능하다.

### 결정적 제약 2: AX는 현재 Space의 창만 열거한다

측정 중 여러 앱이 "창을 잃는" 현상을 추적한 결과다.

| 앱 | 전체 창 | 현재 화면 | AX |
|---|---|---|---|
| Notion | 2 | 0 | 0 |
| Xcode | 1 | 0 | 0 |
| IINA | 4 | 0 | 0 |
| Discord | 2 | 0 | 0 |
| Safari | 4 | 0 | 0 |
| Claude | 5 | 1 | 2 |

`CGWindowListCopyWindowInfo(.optionAll)`로 세면 창이 살아 있는데 `.optionOnScreenOnly`로는 0이고, AX 개수가 후자와 일치한다. 창을 잃은 것이 아니라 다른 Space에 있는 것이다.

여기서 두 가지가 따라 나온다.

**검증 방법에 대해**: 전체화면 검증은 스스로 측정 환경을 오염시킨다. 앱을 전체화면으로 만들면 macOS가 전용 Space를 만들고 시스템이 그쪽으로 이동한다. 7종을 순차로 돌리면 창들이 여러 Space로 흩어져 뒤에 오는 앱이 AX에서 사라진다. 앞서 관측한 대량 실패는 화면 잠금과 이 현상이 겹친 것이었다.

전체화면 검증은 앱 하나씩 독립적으로 돌리고, 각 실행 사이에 창들이 같은 Space에 있는지 확인해야 유효하다.

**제품에 대해**: restage는 현재 Space에 있는 창만 배치할 수 있다. 사용자가 데스크탑을 여러 개 쓰면 다른 데스크탑의 앱은 조회조차 되지 않는다. 앞서 정리한 "데스크탑 지정 불가"가 배치 대상 선정까지 확장되는 셈이다. 이 제약은 yabai 선택 의존을 도입할 때 함께 풀린다.

### 부수 발견: 화면 잠금

잠긴 화면에서는 AX가 어떤 앱의 창도 열거하지 못한다. 초기 구현은 이때 모든 항목을 "창이 뜨지 않았습니다"로 보고해 원인을 완전히 감췄다. probe가 실행 전에 잠금 상태를 확인하고 사유를 밝히며 멈추도록 고쳤다.

긴 검증을 돌릴 때는 잠금을 막아야 한다.

```
caffeinate -d -i -t 1200
```

## 후속 검증에서 추가로 잡은 것

### `AXMinSize`를 노출하지 않으면서 최소 크기를 강제하는 앱

Xcode를 프로젝트가 열린 상태로 검증하려고 `--warm-only` 옵션을 추가했다. probe가 항상 콜드 스타트부터 하기 때문에 앱을 종료해버려 실제 사용 상태를 검증할 방법이 없었다.

프로젝트를 열면 Xcode는 정상적인 창(`1400x900`, `AXStandardWindow`, `sizeSettable=true`, 전체화면 버튼 있음)을 갖는다. 그런데 배치하면 너비가 940에서 멈춘다.

직접 확인한 결과 Xcode는 최소 너비 940을 강제하면서 `AXMinSize` 조회에는 `-25205`(속성 미지원)를 반환한다. 800x900을 요청하면 940x900이 되고 600x700을 요청하면 940x700이 된다. 높이는 요청대로 바뀐다.

기존 제약 판별은 `AXMinSize`에만 의존해서 이걸 못 잡고 `FAIL`로 보고했다. 동작으로 판별하도록 보완했다. 한 축은 요청대로 맞았는데 다른 축만 요청보다 크게 고정됐다면, 앱이 크기 변경 자체는 받아들였다는 뜻이므로 남은 축의 차이는 앱이 막은 것이다.

같은 판별로 KakaoTalk의 최소 높이 640도 드러났다(`q1` 슬롯에서만 나타난다).

### 추론 판별이 만든 오진과 그 교정

이 추론을 넣자마자 잘못된 사유가 하나 나왔다. 전체화면에 갇힌 Claude를 "최소 크기 1728x1084"로 보고한 것이다. 최소 크기가 아니라 전체화면 크기였다.

두 겹으로 막았다.

- 창이 전체화면이면 최소 크기 판별에 들어가기 전에 전체화면을 사유로 보고한다.
- 추론 판별은 위치가 목표와 일치할 때만 적용한다. 위치까지 어긋났다면 크기 제약이 아니라 다른 문제이고, 그때 최소 크기라고 보고하면 원인을 감춘다.

### 다른 Space의 창과 창 없음의 구분

전체화면에 갇힌 앱은 AX에서 창 0개로 보여 "창이 뜨지 않았습니다"로 보고됐다. 창은 멀쩡히 존재하는데 사유가 사실과 달랐다.

`CGWindowList`는 Space와 무관하게 창을 보므로 AX 결과와 대조하면 둘을 구별할 수 있다. 이제 "창 4개가 다른 Space에 있어 접근할 수 없습니다"로 보고한다.
