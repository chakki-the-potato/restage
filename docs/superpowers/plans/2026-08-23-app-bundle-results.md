# 앱 번들과 로그인 시 자동 실행 — 검증 결과

측정일: 2026-08-23

## 만든 것

`scripts/make-app.sh`가 릴리스 바이너리를 빌드하고 `build/restage.app` 번들을 조립한다. SwiftPM은 앱 번들을 만들지 못하므로 구조를 직접 만든다.

번들이 필요한 이유는 둘이다.

- 로그인 시 자동 실행(`SMAppService`)이 앱 번들을 요구한다.
- Finder에서 더블클릭으로 실행하려면 번들이어야 한다.

`LSUIElement`를 켜서 Dock 아이콘 없이 메뉴바에만 뜬다.

### 번들에서는 인자 없이 메뉴바로 뜬다

`LaunchContext.isInsideAppBundle`로 판별한다. Finder 더블클릭이나 로그인 항목으로 실행하면 인자가 오지 않기 때문이다. 터미널에서 실행하면 번들 밖이므로 기존대로 usage를 출력한다.

```
open build/restage.app        → 메뉴바
.build/debug/restage          → usage
```

### 메뉴에 추가된 것

- **접근성 권한을 허용하세요** — 승인 전에만 맨 위에 뜬다. 누르면 시스템 설정을 연다.
- **로그인 시 자동 실행** — 번들에서 실행할 때만 보인다. 체크 상태가 현재 등록 여부를 나타낸다.

## 검증

메뉴 내용을 AX로 직접 읽어 확인했다. 6단계에서는 사람이 봐야 했는데, 상태바 항목에 `AXPress`를 보내고 메뉴 항목을 열거하는 방법을 찾았다.

```
접근성 권한을 허용하세요 | enabled=true
broken                  | enabled=false
dev   ⌃⌥⌘1              | enabled=true
research   ⌃⌥⌘2         | enabled=true
로그인 시 자동 실행       | enabled=true
config 폴더 열기         | enabled=true
종료                    | enabled=true
```

단축키 표시, 깨진 config 비활성화, 로그인 항목 노출이 모두 확인된다.

## 결정적 제약: adhoc 서명은 업데이트마다 승인이 날아간다

### 1. 번들은 별도 TCC 주체다

메뉴 맨 위에 "접근성 권한을 허용하세요"가 떴다. 터미널에서 실행하던 CLI는 터미널 앱의 승인을 상속했지만, 번들 앱은 자기 이름으로 승인을 받아야 한다.

1단계에서 Swift 단일을 고른 근거가 "바이너리가 하나면 승인도 하나"였다. 번들 도입으로 그 전제가 바뀌었다. 다만 CLI와 번들이 같은 바이너리를 쓰므로 사용자가 실제로 승인할 대상은 여전히 하나다.

### 2. 재빌드할 때마다 승인이 무효화된다

`codesign --sign -`(adhoc)은 designated requirement가 코드 해시에 묶인다.

처음에는 "코드가 바뀔 때만 해시가 바뀐다"고 기록했으나 **틀렸다.** 실제로는 컴파일이 일어나면 소스가 같아도 해시가 달라진다.

```
1차 빌드           a6ce3f61
문자열 하나 변경    cd537b06
소스 되돌린 뒤      926e74c5   <- 소스는 1차와 동일한데 해시가 다름
```

처음 측정에서 "변경 없이 재빌드 → 동일"이 나온 것은 SwiftPM이 캐시를 써서 실제로 컴파일하지 않았기 때문이다. 바이너리가 그대로였으니 해시도 그대로였을 뿐이다.

식별자를 `com.chakki.restage`로 고정해도 소용없다. 따라서 **재빌드할 때마다 사용자가 접근성 권한을 다시 켜야 한다.**

이 제약은 검증 중 실제로 겪었다. 실험용 빌드를 되돌린 뒤 재빌드하지 않은 상태에서 승인을 요청해, 승인된 신원과 실행 중인 앱이 어긋났다. `tccutil reset Accessibility com.chakki.restage`로 기록을 지우고 다시 승인해야 했다.

개발 중에는 번들 대신 CLI를 쓰는 편이 낫다. 터미널에서 실행하면 터미널 앱의 승인을 상속하므로 재빌드해도 유지된다.

실제 배포에는 Developer ID 인증서가 필요하다. 그것으로 서명하면 designated requirement가 팀 식별자 기반이 되어 업데이트해도 승인이 유지된다.

유료 Apple Developer 계정이 있어야 하므로 이 저장소에서는 해결할 수 없다.

## 하지 않은 것과 이유

### 공증과 Homebrew cask

Developer ID 인증서와 공개 릴리스가 필요하다. 위와 같은 이유로 불가하다.

### yabai 선택 연동

만들 수는 있으나 **검증이 전혀 불가능하다.** yabai가 설치되어 있지 않고, 동작하려면 SIP 부분 해제가 필요한데 그것은 사용자 결정이다.

1단계 스펙에서 멀티 디스플레이를 미룬 근거가 "검증할 수 없는 경로이므로 구현하지 않는다"였고, 3단계에서 외장 모니터가 있어 검증 가능해졌을 때 넣었다. yabai 연동을 지금 넣으면 그 원칙을 깨는 첫 코드가 된다.

순서는 SIP 해제 결정 → yabai 설치 → 연동이다. 앞의 둘이 선행되어야 한다.

### 편집 화면

앱 피커, slot 선택, 드래그 정렬을 포함한 스키마 CRUD 폼이다. 분량이 한 단계 전체와 맞먹고, 6단계에서 확인했듯 GUI는 자동 검증이 되지 않는다.

얻는 것은 YAML 몇 줄 편집을 대신하는 것이다. `restage list`가 오류 위치를 정확히 짚고 메뉴에서 config 폴더도 열 수 있어 현재도 막히지 않는다. 비용 대비 값이 낮다고 판단했다.

## 사용법

```
./scripts/make-app.sh          build/restage.app 생성
open build/restage.app         메뉴바 실행
```

`build/`는 `.gitignore`에 넣었다.
