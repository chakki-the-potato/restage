# 7단계 검증 결과 — 전역 단축키

측정일: 2026-08-23

## 결과

### 등록과 발화

`dev.yaml`에 `ctrl+alt+cmd+1`, `research.yaml`에 `ctrl+alt+cmd+2`를 넣고 메뉴바를 띄운 뒤 합성 키를 보냈다.

```
등록 2건: dev=registered(key: "1"), research=registered(key: "2")
>>> 단축키 발화: dev
>>> 단축키 발화: research
```

둘 다 등록되고 둘 다 발화했다.

### 중복 충돌

두 워크스페이스에 같은 조합을 넣었다.

```
등록 2건: research=conflicted(key: "1"), dev=registered(key: "1")
```

하나만 등록되고 나머지는 `conflicted`로 보고된다. 한쪽의 실패가 다른 쪽 등록을 막지 않는다.

### 형식 오류

`hotkey: "hyper+9"`를 넣었다.

```
등록 2건: dev=registered(key: "1"),
         research=invalid(reason: "hotkey 형식이 올바르지 않습니다: 'hyper+9'.
                          알 수 없는 수식키입니다: hyper. 가능한 값: cmd, ctrl, alt, shift")
```

조용히 무시되지 않고 어느 값이 왜 틀렸는지 나온다. 다른 워크스페이스의 등록은 그대로 진행된다.

### 단위 테스트

`HotkeySpec.parse`와 `displayString`을 8개 테스트로 덮었다. 수식키 순서·대소문자·별칭, 지원 키 목록, 수식키 없음, 알 수 없는 수식키, 알 수 없는 키, 표시 문자열 정렬.

## 자동 검증이 가능했던 이유

6단계 메뉴바는 클릭 결과를 사람이 봐야 했다. 7단계는 그렇지 않다.

**합성 키 입력으로 Carbon 단축키가 발화한다.** 3단계에서 Space 전환 단축키는 합성 입력으로 동작하지 않았는데, 그것은 시스템이 처리하는 단축키라 합성 이벤트를 무시하기 때문이다. Carbon `RegisterEventHotKey`는 앱 수준 등록이라 일반 이벤트 경로를 탄다.

덕분에 등록·충돌·형식 오류 세 경로를 모두 사람 손 없이 확인했다.

## 검증 중 바로잡은 것

### 잘못된 검증 방법

처음에는 단축키 발화 후 `probe --app safari --slot left-half --warm-only`로 위치를 확인하려 했다. 그런데 그 명령이 **스스로 Safari를 좌측 절반으로 옮긴다.** 단축키가 한 일인지 probe가 한 일인지 구별할 수 없는 검증이었다.

읽기 전용 위치 조회로 바꿨더니 이번에는 Safari 창이 3개라 그중 하나가 이미 목표 위치에 있어 또 판정이 되지 않았다.

결국 발화 자체를 직접 찍는 방식으로 바꿔서 확정했다. **관측 대상을 바꾸지 않는 방법을 쓰거나, 아예 원인 지점을 직접 관측해야 한다.**

### `NSMenuItemBadge`는 macOS 14부터다

메뉴 항목에 단축키를 배지로 붙이려 했으나 배포 타겟이 macOS 13이라 쓸 수 없다. 제목 뒤에 기호를 덧붙이는 방식으로 바꿨다.

## 알려진 한계

- 단축키는 `restage menubar`가 실행 중일 때만 동작한다. CLI는 등록하지 않는다. 명령이 끝나면 프로세스가 사라지므로 등록해도 의미가 없다.
- 다른 앱이 이미 쓰는 조합은 등록되지 않는다. 어느 앱이 쓰는지는 알 방법이 없어 사유에 적지 못한다.
- 로그인 시 자동 실행이 없으므로 재부팅하면 직접 `restage menubar`를 실행해야 한다. 앱 번들과 함께 배포 사이클에서 다룬다.
