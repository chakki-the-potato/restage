# 창 선택 — 설계와 검증 결과

측정일: 2026-08-23

## 문제

6단계 실사용에서 드러났다. `{type: app, app: safari, slot: left-half}`가 Safari의 **시작 페이지 창**을 옮겼다. 그 시점에 Safari에는 창이 둘(시작 페이지, 워크스페이스 전용)이었다.

1단계에서 정한 "창이 여러 개면 가장 최근 활성 창을 배치한다"가 그대로 동작한 것이지만, 브라우저처럼 창을 여러 개 쓰는 앱에서는 **어느 창이 옮겨질지 예측할 수 없다.**

## 해결

앱 항목에 `title`을 선택적으로 둔다. 창 제목의 일부를 적으면 그 창만 대상으로 삼는다.

```yaml
items:
  - {type: app, app: safari, slot: left-half, title: 시작 페이지}
  - {type: app, app: safari, slot: right-half, title: Example}
```

없으면 기존대로 가장 최근 활성 창을 고른다. 기존 config는 그대로 동작한다.

매칭은 대소문자를 가리지 않는 부분 일치다. 여럿이 걸리면 그중 가장 최근 활성 창을 쓴다.

`BrowserItem`의 `window: shared | separate`와 키 이름을 나눈 이유는 둘이 다른 개념이기 때문이다. 브라우저는 어느 창에 탭을 넣을지, 앱은 어느 창을 옮길지를 정한다.

## 계층

파싱 결과는 OS에 의존하지 않는 `WindowSelector`로 표현한다. AX 호출은 `WindowWaiter` 안쪽에만 있다.

```swift
public struct WindowSelector: Sendable, Equatable {
    public let titleContains: String?
    public static let mostRecentlyActive = WindowSelector(titleContains: nil)
}
```

`WindowEngine.waitForWindow`가 `selector`를 받도록 바꿨다. 구현이 하나뿐이고 호출부가 넷이라 프로토콜 변경 비용이 작다.

## 검증

### 단위 테스트

6개를 추가해 97개가 됐다. `title` 없을 때 기본값, 항목별 독립성, 오류 메시지가 실제 창 목록을 담는지.

### 통합 검증

두 창을 **서로 반대 자리로 강제 이동**한 뒤 복원되는지 봤다.

```
강제 이동 후 실행 → placed 2
복원 후:
  시작 페이지    -> 0,33 864x1060
  Example Domain -> 864,33 1728x1060
```

제목대로 각 창이 제 자리를 찾았다. 2회차는 `alreadySatisfied 2`로 창이 움직이지 않는다.

## 검증 중 발견해 수정한 것

### 1. 멱등 판정이 엉뚱한 창을 보고 통과시켰다

첫 검증에서 두 항목 모두 `alreadySatisfied`가 나왔다. 창이 실제로 제 자리에 있어서가 아니었다.

`CurrentState.isPlaced(pid:target:)`는 **그 앱의 아무 창이나** 목표에 있으면 참을 낸다. Safari 창이 이미 좌우에 하나씩 있었으므로, 어느 창이 어디 있든 두 판정이 모두 통과했다. 창을 서로 바꿔 놓아도 "이미 목표 상태"라고 답했을 것이다.

제목을 지정한 항목은 이 빠른 판정을 쓰지 않고, 창을 먼저 찾은 뒤 **그 창의 좌표**를 직접 비교하도록 고쳤다.

이 오진은 결과 표가 알려줬다. 창을 뒤바꿔 놓았는데도 `alreadySatisfied`가 나오는 것이 이상해서 들여다봤다.

### 2. "열린 창이 없습니다"가 사실이 아니었다

없는 제목을 지정했을 때 이렇게 나왔다.

```
제목에 '존재하지않는창'를 포함한 창을 찾지 못했습니다. 열린 창이 없습니다
```

Safari에는 창이 둘 있었다. 타임아웃 후 창 목록을 다시 조회하는데, 그 시점에 Safari가 최전면이 아니라 AX가 빈 배열을 돌려준 것이다. 1단계부터 알고 있던 동작인데 여기서 다시 밟았다.

폴링 중에 본 제목을 기억해두도록 고쳤다.

```
제목에 '존재하지않는창'를 포함한 창을 찾지 못했습니다. 열린 창: Example Domain, 시작 페이지
```

실제 창 제목이 나오므로 사용자가 바로 고칠 수 있다.

### 3. 분류가 틀렸다

제목 불일치를 `unreachable`로 보고했다. `CurrentState.windowCount > 0`이면 무조건 그렇게 분류했기 때문이다.

`unreachable`은 "다른 Space에 있어 손댈 수 없다"는 뜻으로만 써야 한다. 제목이 안 맞는 것은 config를 고치면 되는 문제이므로 `failed`가 맞다.

## 알려진 한계

- 제목은 앱이 바꾼다. 브라우저 창 제목은 활성 탭에 따라 변하므로, 탭을 바꾸면 매칭이 깨질 수 있다. 안정적인 부분 문자열을 고르는 것은 사용자 몫이다.
- 제목이 같은 창이 여럿이면 가장 최근 활성 창을 쓴다. 더 정밀한 지정 방법은 두지 않았다.
