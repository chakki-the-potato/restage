# restage 6단계 설계 — 메뉴바 UI

작성일: 2026-08-23
스코프: 전체 스펙 8절 작업 순서의 6단계 중 메뉴바 부분
선행: `2026-08-23-workspace-registry-design.md` (5단계)
상태: 승인됨

## 1. 목표

메뉴바에서 워크스페이스를 클릭해 실행한다.

완료 기준은 다음과 같다.

- `restage menubar`로 메뉴바 아이콘이 뜬다.
- 메뉴에 등록된 워크스페이스가 나열되고 클릭하면 실행된다.
- config 파일을 고치면 재시작 없이 메뉴에 반영된다.
- 깨진 config도 숨기지 않고 사유와 함께 보여준다.
- 실패가 있으면 알린다.

## 2. 스코프

**포함** — 메뉴바 아이콘, 워크스페이스 목록, 클릭 실행, 실패 알림, config 폴더 열기.

**제외**

- 편집 화면. 전체 스펙 6단계에 포함되어 있으나 이번 사이클에서 뺐다. 앱 피커, slot 선택, 드래그 정렬을 포함한 스키마 CRUD 폼이라 분량이 따로 놀고, YAML을 손으로 쓰는 편이 지금은 더 빠르다.
- 단축키 바인딩 (7단계).
- 로그인 시 자동 실행. 앱 번들이 필요하므로 배포 사이클에서 다룬다.

## 3. 구조 — 단일 바이너리에 서브커맨드

`restage menubar`가 메뉴바를 띄운다. 인자가 있으면 기존대로 CLI로 동작한다.

별도 실행 파일을 만들지 않는 이유는 접근성 권한 때문이다. 1단계에서 Swift 단일을 고른 근거가 "바이너리가 하나면 승인도 하나"였는데, 메뉴바를 별도 바이너리로 만들면 사용자가 승인을 두 번 해야 하고 업데이트마다 둘 다 재승인된다. 그 근거를 여기서 깨뜨릴 이유가 없다.

### 3.1 SwiftUI를 쓰지 않는 이유

SwiftPM 실행 타겟은 `main.swift`와 `@main`을 동시에 가질 수 없다. 현재 `main.swift`가 CLI 명령을 분기하므로 SwiftUI의 `App` 생명주기(`MenuBarExtra`)를 쓸 수 없다.

`NSStatusItem`으로 직접 구성하면 이 제약이 사라진다. SwiftPM 실행 파일에서 `main.swift`와 함께 동작함을 실제로 확인했다. 상태바 항목이 생성되고 `button`과 `isVisible`이 모두 참이었다.

메뉴 구성이 목록과 몇 개의 동작뿐이라 SwiftUI가 주는 이득도 없다.

## 4. 메뉴 구성

```
dev
research
broken            (비활성, 오류 사유가 툴팁)
─────────────
config 폴더 열기
종료
```

워크스페이스가 하나도 없으면 목록 자리에 비활성 안내 항목을 둔다.

```
등록된 워크스페이스가 없습니다
─────────────
config 폴더 열기
종료
```

디렉토리 자체가 없으면 안내 문구를 그에 맞게 바꾼다.

## 5. 매번 다시 만든다

`NSMenuDelegate.menuWillOpen`에서 메뉴를 비우고 `WorkspaceRegistry.list()`를 다시 조회해 채운다.

메뉴를 한 번만 만들면 config 파일을 고친 뒤 앱을 재시작해야 한다. 파일을 직접 편집하는 것이 이 도구의 편집 방식이므로, 재시작이 필요하면 쓰기 어렵다.

목록 조회는 파일 몇 개를 파싱하는 정도라 메뉴를 여는 순간에 해도 체감되지 않는다.

## 6. 깨진 config

CLI의 `restage list`와 같은 원칙을 따른다. 목록에서 빼지 않고 비활성 항목으로 남기며 오류 사유를 툴팁에 넣는다.

목록에 없으면 사용자는 파일이 없는 줄 알고 엉뚱한 곳을 찾는다. 이는 1~5단계에서 반복해 확인한 실패 방식이다.

## 7. 실행과 피드백

메뉴 항목을 클릭하면 해당 워크스페이스를 실행한다. 흐름은 `restage open <name>`과 동일하며 `WorkspaceRunner`를 그대로 쓴다.

**실패가 있을 때만 알린다.** GUI 프로세스라 stdout이 보이지 않으므로 `NSAlert`로 어느 항목이 왜 실패했는지 띄운다. 전부 성공하면 아무것도 띄우지 않는다. 워크스페이스가 눈앞에 배치되는 것 자체가 피드백이다.

알림 대상은 `OutcomeStatus.isSuccess`가 거짓인 항목이다. `constrained`와 `alreadySatisfied`는 성공으로 세므로 알리지 않는다.

실행 중에는 중복 실행을 막는다. 실행이 끝나기 전에 다른 항목을 누르면 무시한다.

## 8. 접근성 권한

메뉴바 시작 시 접근성 권한을 확인하고, 없으면 안내 알림을 띄운 뒤 시스템 설정을 연다. CLI의 온보딩 메시지를 그대로 쓴다.

권한이 없어도 메뉴바는 뜬다. 사용자가 승인한 뒤 다시 클릭하면 동작한다.

## 9. 모듈 경계

```
Sources/restage/
  MenuBarCommand.swift     restage menubar 진입점
  MenuBarController.swift  NSStatusItem, 메뉴 구성, 실행과 알림
  main.swift               (수정) menubar 분기 추가
```

`RestageKit`과 `RestageKitDarwin`은 수정하지 않는다. 메뉴바는 기존 `WorkspaceRegistry`, `WorkspaceResolver`, `WorkspaceRunner`, `DisplayCatalog`를 부르는 얇은 껍데기다.

`OpenCommand`와 중복되는 실행 흐름은 공유하지 않는다. `OpenCommand`는 종료 코드를 돌려주고 stdout에 표를 찍는 CLI 동작이고, 메뉴바는 알림을 띄우는 GUI 동작이라 출력 방식이 다르다. 흐름이 같아 보이지만 억지로 합치면 양쪽 모두 어색해진다.

## 10. 검증

### 10.1 자동 검증

프로세스 안에서 확인할 수 있는 것만 자동으로 본다.

- 상태바 항목이 생성되고 `button`이 nil이 아니며 `isVisible`이 참
- `menuWillOpen` 후 메뉴 항목 수와 제목이 등록된 워크스페이스와 일치
- 깨진 config 항목이 비활성이고 툴팁에 오류가 담김
- 워크스페이스가 없을 때 안내 항목이 뜸

검증용으로 `--selftest` 같은 플래그를 두지 않는다. 대신 `MenuBarController`가 메뉴를 구성하는 부분을 순수 함수로 분리해 단위 테스트한다. `NSMenu`를 만들어 검사하는 것은 `@MainActor` 테스트로 가능하다.

### 10.2 사람이 확인해야 하는 것

클릭해서 실제로 배치되는지는 자동으로 확인할 수 없다. 다음은 사용자가 직접 봐야 한다.

- 메뉴바에 아이콘이 보이는지
- 클릭하면 목록이 뜨는지
- 항목을 누르면 워크스페이스가 배치되는지
- 실패가 있을 때 알림이 뜨는지

지금까지 5단계 내내 자동 검증으로 진행했으나 GUI는 그 방식이 통하지 않는다. 이 한계를 감추지 않고 명시한다.

## 11. 후속 사이클에 남기는 것

- 편집 화면. 앱 피커, slot 선택, 드래그 정렬.
- 단축키 바인딩 (7단계). config의 `hotkey` 필드를 사용한다.
- 앱 번들과 로그인 시 자동 실행. 공증과 Homebrew cask 배포도 함께.
- Space 지정. yabai 선택 의존.
